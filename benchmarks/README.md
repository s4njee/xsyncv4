# Performance evidence

P3 benchmarks run directly between neo (Raspberry Pi 5, ext4) and freya
(x86_64, ZFS). Results and metadata belong in `results/`; source corpora and
transfer destinations stay in benchmark-owned remote directories. The current
static `xs` releases are staged there with explicit paths.

`run.py` alternates xs and rsync order, records wall time, CPU and peak RSS
for the client and remote helper, and checks every result with a checksum
rsync dry run. Setup, deletion of owned destinations and verification are not
timed. A nonzero transfer or nonempty verification output fails the run.
The JSON file is updated after every verified sample and marked complete only
after every requested scenario finishes.

`bench/bench.py --target host:absolute-root` invokes this SSH runner. Pass
`--corpus`, `--work`, `--remote-xs`, `--remote-measure` and `--output`;
`--direction=push` or `pull` controls data flow. The two hosts use the same
absolute corpus path for these paired runs. Neo can authenticate to freya,
so both data directions can be measured without changing SSH authorization.

The default cache policy retains existing OS caches; it does not imply that
a corpus larger than RAM is entirely resident. A `cold` run requires explicit
reset commands on both endpoints. A cache-reset command is not proof of a cold ZFS workload: ARC residency
and storage reads must be verified independently. The Linux ARC shrinker
respects an ARC minimum when reclaiming clean buffers; see the
[OpenZFS implementation](https://github.com/openzfs/zfs/blob/zfs-2.4.3/module/os/linux/zfs/arc_os.c).

The initial Congress-slice/APFS table in the main README is historical. New
measurements identify source revisions, architectures, filesystems, corpus
sizes, tool versions and verification outcomes. They must not be merged with
old results without those labels.

The first paired run is `20261010T144748Z-715fa0`; its
[result table](results/20261010T144748Z-715fa0-summary.md) includes only completed,
verified cases. [The manifest](results/20261010T144748Z-715fa0-run-manifest.json)
records the source revision, harness hashes and dataset counts. Congress is
the entire available `congress/data` snapshot, 10.53 GB in 914,106 files; the
historical backlog estimate of 14 GB does not match this snapshot. Its update
fixture replaces 9,141 files (approximately 1%) without changing the baseline.

Both full-corpus directions have completed all 24 verified samples each.
With retained caches, checksum re-sync is 2.28x faster than rsync from neo to
freya and 2.16x faster from freya to neo. No-op results differ by direction:
xs takes 26.37 s versus rsync's 19.54 s pushing, and 27.79 s versus 80.30 s
pulling. The linked table retains fresh-copy regressions and memory costs too.
The 1% update push completes all six verified samples: xs takes 26.99 s versus
rsync's 31.59 s (1.17x). The reverse update completes six verified samples:
xs takes 30.64 s versus rsync's 82.85 s (2.70x). Cold-cache measurements remain
pending access to reset and verify freya's ZFS cache.

To reproduce the paired run with already prepared owned fixtures:

```sh
python3 benchmarks/pair.py --runs 3
python3 benchmarks/report.py --run-id RUN_ID --output benchmarks/results/RUN_ID-summary.md
```

`pair.py` reads the explicitly staged host/root information from
`.bench/p3-state.json`. It runs one case at a time and resumes cases whose local
JSON is not marked complete. Do not start another runner against the same work
directory; `run.py` holds an exclusive lock to protect its destinations.
For a long-running case, `python3 benchmarks/checkpoint.py --dataset congress
--direction push` fetches its verified incremental JSON without restarting the
job. Partial cases remain excluded from the summary table.

CPU includes waited-for descendants. RSS uses `wait4` resource high-water
marks, which report the largest process rather than simultaneous memory of
the complete process tree on Linux; see [getrusage(2)](https://www.man7.org/linux/man-pages/man2/getrusage.2.html).
Tables select the larger process peak from the two endpoints. Dataset
directory inventories exclude the dataset root; logical bytes count regular files.

`python3 benchmarks/test_harness.py` checks destination ownership, concurrent
run rejection, independent corruption detection and transparent wire/status
measurement. `snapshot.py --target user@host --output path.json` records small
read-only load, memory, block-I/O and ZFS ARC snapshots for cache interpretation.

`stream_probe.py` measures an exact-length stream of memory-generated bytes over
SSH with compression disabled and no file reads or writes in the timed path.
Stage it alongside `measure.py` under the owned root's `bin/`, then run it from
neo with `--host sanjee@freya.local --remote-root ROOT --direction push` (or
`pull`) and `--output ROOT/logs/stream-DIRECTION.json`. Run this separately
from corpus transfers; it helps distinguish cipher/transport capacity from
filesystem work. Both endpoints must receive the exact expected byte count.

The [APFS no-op diagnostic](results/20261010T152712Z-apfs-baseline-summary.md)
records the current binary's cost at 1, 2, 4 and 8 threads. Its host had high
background load and the volume was 98% full; quieter/free-volume measurements
are still required before choosing filesystem defaults. `profile_apfs.py`
samples a separate no-op with `/usr/bin/sample`, then verifies it independently.

`clone_modes.py` compares omitted-permission clones with the pinned old binary,
candidate byte copies and rsync. It requires a fresh owned work directory and
checks every timed result against an untimed rsync oracle, including exact
modes, identities and mtimes. The [completed F-11 comparison](results/20261010-f11-clone-modes-summary.md)
retains both the initial small-file regression and the final improved path.

`deletion.py` compares the prior product, one-worker and four-worker candidates,
and rsync on 65,536 stale files. It covers independent stale subtrees and a
single stale root, rotates tool positions, and verifies every result with
untimed rsync checksums and metadata. Use a fresh owned directory:

```sh
python3 benchmarks/deletion.py --reference /path/to/prior/xs --candidate /path/to/current/xs \
  --work .bench/deletion-run --output benchmarks/results/deletion-run.json --rsync /path/to/rsync
```

Fixtures and logs stay in the owned work directory; results identify binary
hashes, versions, load and free space. Partial runs do not establish completion.
The [completed F-12 comparison](results/20261010-f12-deletion-summary.md) records
all 32 verified samples, the single-root result and the additional CPU cost.

`large_files.py` compares the prior product, one- and four-worker candidates,
and rsync on two-file and single-file fixtures. It covers local byte copies,
automatic kernel copies, and plain/compressed pipe transfers. Each tool gets
one verified warmup and four samples in rotated orders. The random file has
different bytes in every MiB. A fresh owned work directory is required:

```sh
python3 benchmarks/large_files.py --reference /path/to/prior/xs --candidate /path/to/current/xs \
  --work .bench/large-run --output benchmarks/results/large-run.json --rsync /path/to/rsync
```

Use `--file-mib` to change file size and `--cases` to select known cases.
`--candidate-jobs 0` measures automatic worker selection; the default value 4
requests intra-file ranges explicitly. The one-worker control is always kept.
The [revision 98eeb171c94d comparison](results/20261010-f05-98eeb17-summary.md)
retains all 336 timed samples across macOS, Linux overlay and loop-backed btrfs,
including single-file regressions. The [completed F-05 comparison](results/20261010-f05-7c3072c-summary.md)
records restored defaults across all seven cases on three filesystems and
explicit range selection with `-jN`. Reflink correctness passes on actual btrfs
and XFS volumes with both final glibc and static-musl products. The expanded
hosted gate remains a separate acceptance check for the product.

## Regression gate

`.github/workflows/performance.yml` builds the pinned reference and candidate
with the same Release configuration on each Linux and macOS runner. It measures
18 scenarios: fresh/no-op/checksum/1% update locally and through the pipe
transport, compressed pipe copies, large copies and a tiny pipe transfer.
Single-file local byte/plain-pipe/compressed-pipe cases protect range scheduling
separately from file-level parallelism. Local `-rt`/`-rlt` cases also protect F-11's clone improvements; fixtures include
read-only and umask-sensitive file modes.
Each tool receives one verified warmup excluded from the ratios and 24 samples
in four complete cycles of all six orders, with independent rsync
checksum/metadata verification after every sample. Setup is untimed.
The fixed production matrix collects 1,296 timed samples and 54 warmups per
platform. All samples contribute to the medians; failures do not trigger
selective retries. The larger sample count addresses the substantial timing
variation observed on shared macOS runners.
The measurement step has a 90-minute limit inside a 120-minute job, leaving
time to upload partial evidence when the measurement step times out.

For each scenario, the job records a minimum speedup relative to rsync equal
to 85% of the pinned reference's measured speedup on that same runner. It exits
nonzero if any candidate speedup falls below its recorded minimum, or if any
transfer or verification fails. This allows 15% timing variation; the emitted
JSON records the actual floor, all samples, resource metrics, binary hashes
and source versions. Pipe cases use `tests/fakessh.sh` on the runner. The
physical neo/freya measurements are retained separately in `results/`.

`ci-policy.json` pins the reference commit. After a performance improvement is
verified, advance that reference to the tested product commit so later changes
protect the new performance. CI builds both revisions before measuring, and
rejects a reference binary that does not identify the pinned clean revision.
Actions upload the result JSON even when the gate fails. Artifact names identify
the platform and workflow run.

`python3 benchmarks/ci_gate_test.py --xsync build/xs --rsync /path/to/rsync`
exercises real transfers with a healthy binary, an intentionally delayed binary
and a corrupt binary that exits successfully. Its small fixtures, relaxed test policy and
24-sample healthy comparison validate gate behavior on busy developer machines; CI's production
measurements use the checked-in 24-sample, 85% policy and larger fixtures.
