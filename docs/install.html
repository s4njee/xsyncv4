xs-install(1) ​

Install & releases

Clone and build from GitHub, install locally, build static release binaries, and put the helper on the machines you sync with.

FROM SOURCE ​

xs is installed from its source repository. These commands go from nothing to an installed xs on macOS or on Debian and Ubuntu. Getting started explains each step, and the CMake version needed (3.24 or later).

macOS
sh
xcode-select --install
brew install git cmake ninja zstd xxhash icu4c
git clone https://github.com/s4njee/xsyncv4.git
cd xsyncv4
cmake -S . -B build -G Ninja
cmake --build build
cmake --install build --prefix "$HOME/.local"
export PATH="$HOME/.local/bin:$PATH"
xs --version
Debian / Ubuntu
sh
sudo apt update
sudo apt install git build-essential cmake ninja-build python3 libzstd-dev libxxhash-dev libicu-dev
git clone https://github.com/s4njee/xsyncv4.git
cd xsyncv4
cmake -S . -B build -G Ninja
cmake --build build
cmake --install build --prefix "$HOME/.local"
export PATH="$HOME/.local/bin:$PATH"
xs --version

To update later, run git pull in xsyncv4, then the cmake --build and cmake --install lines again.

LOCAL INSTALL ​

From inside the cloned xsyncv4 directory, after building
sh
cmake --install build --prefix "$HOME/.local"
export PATH="$HOME/.local/bin:$PATH"

This installs xs, a manpage generated from its own --help, and zsh completion. The completion builds on zsh’s rsync completion. For zsh, add fpath=("$HOME/.local/share/zsh/site-functions" $fpath) before compinit in .zshrc. Release binaries already in dist/ are installed too, under share/xs/releases/, for remote install.

HOMEBREW (LOCAL TAP) ​

From inside the cloned xsyncv4 directory: a formula for this checkout, in a tap on your machine
sh
python3 tools/package.py
brew tap-new xs/local
cp dist/homebrew/Formula/xs.rb "$(brew --repository xs/local)/Formula/"
brew install --build-from-source xs/local/xs
brew test xs/local/xs

The formula points at a source archive of this checkout and builds the vendored, hash-checked dependencies. No public tap is published. If the tap already exists, skip tap-new, and use brew reinstall to replace an installed copy.

RELEASE BINARIES ​

From inside the cloned xsyncv4 directory: static binaries for every supported target
sh
cmake --preset release-static
cmake --build --preset release-static
OutputTargetLinks against
dist/xs-linux-amd64Linux x86-64nothing: fully static, built with musl
dist/xs-linux-arm64Linux ARM64, such as a Raspberry Pi 4 or 5 on a 64-bit OSnothing: fully static, built with musl
dist/xs-darwin-universalmacOS on Apple silicon and IntelApple system libraries only
dist/manifest.jsonSHA-256 of each binary

The preset needs CMake 3.24+, Ninja, a C/C++ compiler, GNU make and Docker with Linux amd64/arm64 emulation. A Linux host can build the two Linux binaries; the macOS binary needs a macOS host. zstd, xxHash and ICU are vendored as hash-checked source archives. xs --version includes the source revision, with -dirty for modified sources. No binaries are published for download yet.

Check a binary against the manifest
sh
python3 -c "import json; print(json.load(open('dist/manifest.json'))['xs-linux-arm64']['sha256'])"
shasum -a 256 dist/xs-linux-arm64

REMOTE INSTALL ​

Native transfers need xs on both machines. --install is the only way xs ever puts an executable on another host: transfers never upload one. It runs uname on the host over ssh, picks the matching release binary, and installs it atomically at ~/.local/bin/xs.

Install xs on a host that does not have it, then push natively
sh
export XSYNC_RELEASE_DIR=releases
xs --install user@pi
xs -azi --no-fallback src/ user@pi:backup/ | tail -n 3
ACTUAL OUTPUT · EXIT 0
Installed xs-linux-amd64 on user@pi at ~/.local/bin/xs
xs  version 0.1.0  protocol version 4  git d3a49f8872fd
<f+++++++++ notes.txt
cd+++++++++ scripts/
<f+++++++++ scripts/build.sh

Captured through tests/fakessh.sh, an ssh stand-in that runs the remote side on the same machine.

  • It refuses to replace a newer or unrecognized xs unless --force is given. An interrupted or invalid upload leaves the previous executable in place.
  • Release binaries are looked for beside the local xs, then in a sibling dist/, then in ../share/xs/releases/. XSYNC_RELEASE_DIR names another directory.
  • After installing, transfers find the helper in ~/.local/bin even though it is not on the remote PATH, as the push above shows.

HOW TRANSFERS FIND THE HELPER ​

XSYNC_REMOTE_PATH may contain spaces or start with ~/. An explicit --rsync-path is also used if the transfer falls back, so it must then accept rsync’s server arguments too; prefer the lookup when fallback matters.
