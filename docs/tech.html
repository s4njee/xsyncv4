Tech stack

The language, libraries, hashes, system interfaces and tooling behind xs, and the trade-offs behind each choice.

ABOUT THE REASONS

The repository records what was chosen, not why. The reasons on this page are the engineering trade-offs that apply to each choice, so read them as explanation, not as quotes from a design record. The facts are checked against the source.

WHY C++ ​

Most of xs’s speed comes from operating-system interfaces that only exist as C calls: getattrlistbulk to list a directory with its attributes in one call, clonefile for APFS clones, openat/fstatat with O_NOFOLLOW relative to an anchored directory, and hole punching for sparse files. A language that calls these directly, with no runtime between it and the kernel, keeps the hot path simple. It also yields one self-contained executable that runs on a Raspberry Pi with nothing installed.

  • The standard used. C++20 is used conservatively. Its visible additions here are starts_with/ends_with and contains. The rest is the C++17 standard library: string_view (used throughout), filesystem, optional, threads, atomics and condition variables. There are no coroutines, modules, ranges or concepts. That keeps the code portable across the compilers it is checked with, clang 21 and gcc 12.
  • Dependencies. Only three libraries, all C: zstd, xxHash and ICU. All are vendored, so a release build downloads nothing.
  • The cost: memory safety. C++ does not prevent out-of-bounds reads, and xs parses bytes from another machine. The mitigations are bounds-checked decoders, a size cap on every frame, rejection of frames for features that were not negotiated, and hostile-peer tests (tests/wire_test.py and the *_wire_test.py files). Sanitizer runs and fuzzing of the decoders are still open (backlog Q-04 and Q-05).

HASHING: XXH3, NOT BLAKE3 ​

xs does not use BLAKE3. Every hash in the transfer path is xxHash’s XXH3:

UseHashPurpose
Every F_DATA block on the wireXXH3-64Detects a corrupted or truncated block; the receiver stops with “data corruption detected in transfer stream”.
Delta block signaturesA rolling weak sum, then XXH3-64The weak sum finds candidate blocks quickly; XXH3 confirms them before they are reused.
A rebuilt delta fileXXH3-128Proves the reconstructed file equals the source before it is published.
Resume prefixes (-P)XXH3-128Both sides hash the existing prefix; only a match is reused.
Checksum mode (-c)XXH3-128Compares file contents when size and time match.
Streamed extended attributesXXH3-64Checks large attribute values sent in chunks.

Why a non-cryptographic hash fits. These checks detect accidents: a flipped bit, a truncated stream, a file that changed between scan and read, or a bug. They are not meant to stop an adversary. XXH3 runs at roughly memory-bandwidth speed, so hashing a prefix, a block or a -c pass does not become the bottleneck. Protection against tampering in transit comes from the channel: ssh authenticates both ends and protects every byte cryptographically, so a third party cannot alter data in flight.

Where BLAKE3 would matter. XXH3 does not resist deliberately constructed collisions. If someone who controls file contents could profit from two different blocks or files hashing alike, a cryptographic hash such as BLAKE3 would be the right tool. BLAKE3 is also very fast and parallelizes across cores, though it is slower than XXH3 per core. Examples are content-addressed deduplication across untrusted sources, or treating -c as proof that files are identical. xs has no such mode today. rsync’s own way to choose the hash, --checksum-choice, is one of the options xs hands to rsync. A cryptographic option would be a deliberate, opt-in addition.

The only BLAKE-family hash in the repository is in the test harness: tests/difftest.py compares result trees with Python’s blake2b. It is independent of xs, so a bug in xs’s hashing cannot hide a wrong result there.

COMPRESSION: ZSTANDARD ​

  • Per block. With -z, each 1 MiB data block is compressed on its own, at level 3 unless --compress-level says otherwise, using a compression context per worker thread. Independent blocks let several threads compress and decompress at once. In the measured runs, -z transfers are where xs is furthest ahead.
  • Only remote. A local copy has no connection, so -z does nothing there.
  • Choice. --compress-choice accepts zstd or none. A helper without compression support receives plain data.
  • Not yet adaptive. Incompressible blocks are still compressed, and the level does not follow link speed (backlog F-04).

UNICODE NAMES: ICU ​

macOS filesystems are usually case-insensitive, and they treat different Unicode encodings of one name as the same file. Notes.txt and notes.txt are one file there, and so are two spellings of Résumé.txt whose é is written as one code point in one and as e plus a combining accent in the other. Copying both names into such a directory would silently overwrite one with the other. Before scheduling any write, xs checks names with ICU’s normalization and full case folding and refuses colliding names (backlog T-12). ICU is linked statically with its data, so the check behaves the same everywhere and does not depend on the destination system’s Unicode tables. It is the largest of the three dependencies.

OWN PROTOCOL, RSYNC FALLBACK ​

rsync runs one sender, one generator and one receiver process, and moves files one after another. xs’s protocol is built for parallel workers instead: it streams a listing per directory, answers per directory, and packs many small files into shared blocks. The cost is compatibility: xs must be on both ends, and it cannot talk to rsync daemons. That is why fallback is automatic. A command xs cannot run natively is handed to a real rsync before anything is written. The protocol is versioned with negotiated feature bits, so older helpers keep working (protocol reference).

BUILD AND RELEASE ​

  • CMake and Ninja, Release by default with -O3 and link-time optimization. The manpage is generated from the built binary’s own --help (tools/help_to_man.py).
  • Vendored dependencies. The original zstd, xxHash and ICU source archives are checked in under third_party/, and CMake verifies each one’s SHA-256 before extracting it.
  • Static Linux binaries for amd64 and arm64 are built with musl in Alpine containers under Docker, so they run on any distribution with no installed libraries. The macOS binary is universal (Apple silicon and Intel) and links only Apple system libraries.
  • Traceable. xs --version prints the source revision, with -dirty for modified sources, and dist/manifest.json records each binary’s SHA-256.

TESTING ​

The main test strategy is differential. tests/difftest.py and the area-specific suites build the same fixture twice, run real rsync and xs against it, and compare names, types, contents, modes, nanosecond times, link targets and exit codes. Unit tests cover the filter matcher (a table generated from rsync 3.4.4), attribute storage and sparse writes. Fault injection interposes libc calls (tests/fault_io.cpp) to test races and I/O errors. A two-container Docker rig runs suites over a real sshd. The contributing page has the full matrix.

THIS SITE ​

  • VitePress 1.6.4 for the manual: static pages, local search, no server. Pages render one at a time (buildConcurrency: 1) so the search index, and therefore every asset hash, is reproducible.
  • Python generators build the reference pages from the binary and the source: options, exit codes, protocol constants, benchmarks, development status and the changelog. npm run check fails when any of them drift.
  • Captured output. Every example and recording is real output from the current binary.
  • The product page is hand-written HTML, CSS and JavaScript with vendored HoloCSS motion and a WebGPU fluid background (HoloGPU), which falls back to a static background without WebGPU. Nothing is loaded from the network.
