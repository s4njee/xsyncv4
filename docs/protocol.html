Protocol & compatibility

How xs talks to its remote helper, which features each option needs, and what happens with older helpers.

OVERVIEW ​

xs is not wire-compatible with rsync. A remote transfer runs xs --server on the other machine over a remote shell, normally ssh, and the two processes speak xs’s own pipelined protocol over the shell’s stdin and stdout. Paths travel as protocol data, never as shell text.

Every constant on this page is read from src/common.h and src/remote.cpp when the documentation is built, and npm run check fails if the copy here is out of date.

VERSIONS ​

Each release speaks its own protocol, N, and the one before it, N−1. When a protocol-4 client meets a protocol-3 helper, it reconnects once at protocol 3 before opening the destination. A protocol-3 client can also use a protocol-4 helper. If the versions are further apart, the transfer falls back to rsync, or exits 2 with --no-fallback.

A protocol-3 peer is assumed to support only the core transfer, compression, name mapping and safe links. Any request beyond that (-H, -X, -A, --bwlimit, extended filters, structured output and so on) delegates to rsync before anything is written.

NEGOTIATION ​

  1. The client starts the helper: ssh [-l user] host <helper> --server. The helper is --rsync-path if given; otherwise a small shell snippet tries xs on PATH, then ~/.local/bin/xs, then XSYNC_REMOTE_PATH. If none is found, the shell exits 127 and the transfer falls back to rsync.
  2. The client sends F_HELLO: magic, version, role (the helper receives on a push and sends on a pull), its feature mask, and the frozen options.
  3. The helper answers with its own F_HELLO. The negotiated features are the intersection of both masks. Unknown bits are ignored.
  4. Each side checks that every feature the requested options need is in the intersection. If one is missing, the transfer falls back to rsync before any write, or exits 4 with --no-fallback. Optional features, such as resume or compression, are simply not used.
  5. Options outside the frozen layout follow as separate configuration frames, each sent only when its feature was negotiated: I/O limits, xattrs, ACLs, --chown, sparse, --link-dest, relative paths, file lists, filters, deletion, pruning and output.

FRAMES ​

Every frame is a 4-byte payload length, a 1-byte type and the payload, capped at 1 GiB. Each type has its own length and negotiation checks: a frame for a feature that was not negotiated is a protocol error, never ignored.

A PUSH ​

  1. Handshake and configuration, as above.
  2. The receiving helper sends F_DEST: its destination’s identity. The sender refuses to continue if the destination lies inside the source.
  3. The sender walks the source in parallel and streams one F_DIR per directory, with F_IDMAP names and streamed extended attributes, then F_LIST_END.
  4. For each directory, the receiver compares it with the destination and answers F_NEED: the files it wants, with any verified resume prefix and whether a delta is possible.
  5. The sender reads the needed files on its worker threads. Small files are packed many to a F_DATA block; large files are split into chunks; changed large files can use a delta (F_DELTA_REQUEST, F_DELTA_SIGNATURE, then copy and literal records).
  6. While writing, the receiver reports progress (F_PROGRESS), file events (F_OUTPUT), phases (F_PHASE) and errors (F_MSG).
  7. The sender finishes with F_DATA_END; the receiver finalizes directory attributes and deletions and replies F_DONE.

A pull is the same exchange with the roles reversed: the helper sends, and the client receives and renders output locally. See how it works for a diagram.

FROZEN PROTOCOL-3 LAYOUT ​

The options inside F_HELLO keep the exact layout of protocol 3, so older peers can still parse them.

32 flags, one byte each, in this order:

recursive dirs links copy_links perms times group owner devices specials compress dry_run del delete_excluded force update checksum size_only ignore_times ignore_existing existing one_fs inplace omit_dir_times omit_link_times numeric_ids itemize partial clone direct_new ignore_errors safe_links

Then 7 integers as zigzag varints:

verbose compress_level max_size min_size modify_window jobs max_delete

Then a count and the plain include/exclude rules. Nothing may be added to, removed from or reordered in this layout.

ADDING A FEATURE ​

  • A new optional frame, field or option gets its own feature bit. It must not change the protocol-3 layout or add unnegotiated fields to the Hello.
  • A receiver rejects frames for features that were not negotiated.
  • A requested semantic is never dropped silently. If the peer lacks a feature the user asked for, the transfer falls back or fails before any write.
  • When the supported window moves forward, a frozen N−1 peer is checked in as a fixture, like tests/fixtures/protocol3.tar.gz. Transfers are then tested in both directions, old client to new helper and new client to old helper, with fallback disabled (tests/protocol_test.py).
