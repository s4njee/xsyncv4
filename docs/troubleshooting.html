xs-troubleshoot(7) ​

Troubleshooting

What each fallback notice and common failure means, with the exact text xs prints.

FALLBACK NOTICES ​

When xs cannot do something natively, it runs a real rsync from PATH instead. Before anything is written, it prints one line naming the reason: xs: falling back to rsync: REASON. The transfer still happens, with rsync’s speed, output and behavior. There are three causes, and each one fails in its own way with --no-fallback or XSYNC_FALLBACK=0.

CauseNotice namesWith --no-fallback
An option xs does not implement--backup is not supported by xsexit 1
No xs on the remote hostremote xs is not installed on HOSTexit 127
The remote xs is too old for a requested optionpeer does not support …exit 4

Transfers never fall back once they have started, and malformed protocol data never triggers fallback. --progress=json never falls back either, because rsync cannot produce its events.

An option xs does not implement ​

An option xs does not implement runs rsync instead
sh
xs -a --backup src/ dst/
ls dst/notes.txt*
ACTUAL OUTPUT · EXIT 0
dst/notes.txt
dst/notes.txt~
STDERR
xs: falling back to rsync: --backup is not supported by xs
The same request with fallback disabled
sh
xs --no-fallback -a --backup src/ dst/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 1
STDERR
xs: --backup is not supported by xs (fallback disabled)

The full list is under delegated options. If you need the option and want xs’s speed for everything else, run the two kinds of work as separate commands.

No xs on the remote host ​

No xs on the remote host: rsync carries the transfer
sh
xs -az src/ host:backup/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 0
STDERR
xs: falling back to rsync: remote xs is not installed on host

Captured through tests/fakessh.sh, an ssh stand-in that runs the remote side on the same machine.

No xs on the remote host, fallback disabled
sh
xs --no-fallback -az src/ host:backup/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 127
STDERR
xs: remote xs is not installed on host (fallback disabled)

Captured through tests/fakessh.sh, an ssh stand-in that runs the remote side on the same machine.

Install the helper with xs --install user@host (see remote install), put xs on the remote PATH or in ~/.local/bin, or name it with --rsync-path.

The remote xs is too old ​

A helper without hard-link support, fallback disabled
sh
xs --no-fallback -aH src/ host:backup/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 4
STDERR
xs: connection unexpectedly closed
xs error: exiting (code 12)
xs: peer does not support hard-link preservation (fallback disabled)

Captured through tests/fakessh.sh, an ssh stand-in that runs the remote side on the same machine.

The same helper with fallback enabled
sh
xs -aH src/ host:backup/; echo "exit status: $?"
stat -c "%h links  %n" backup/notes.txt
ACTUAL OUTPUT · EXIT 0
exit status: 0
2 links  backup/notes.txt
STDERR
xs: connection unexpectedly closed
xs error: exiting (code 12)
xs: falling back to rsync: peer does not support hard-link preservation

Captured through tests/fakessh.sh, an ssh stand-in that runs the remote side on the same machine.

The helper here lacks hard-link support. The two lines before the reason are the helper’s own messages, forwarded over ssh when the client ends the session. They do not mean the transfer broke; the client’s line and its exit status are what count. Update the helper with xs --install user@host, which replaces an older version (only a newer or unrecognized one needs --force), or drop the option. The feature table shows which option needs which feature.

REMOTE CONNECTIONS ​

  • Exit 255 is ssh failing to connect or authenticate; xs passes ssh’s status through. Try the same ssh command by hand. Options for ssh itself go in -e, for example -e "ssh -p 2222 -i ~/.ssh/backup_key".
  • Exit 12 with connection unexpectedly closed (remote shell exited with code N) means the remote shell ended with some other status, for example a login script that exits or prints errors.
  • Exit 30 is the --timeout deadline. It counts idle time only, so a slow but moving transfer does not trip it.
  • Exit 2 means the two versions are too far apart to talk. Each release speaks its own protocol and the previous one.
  • Password and passphrase prompts come from ssh and work as they do with rsync. For unattended runs, use keys or an agent.

TRANSFER RESULTS ​

Exit 23: some files were not transferred ​

A source that does not exist
sh
xs -a missing/ dst/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 23
STDERR
xs: link_stat "missing/" failed: No such file or directory (2)
xs: error summary: 1 error (showing first 1)
  partial transfer (code 23): 1 error
    link_stat "missing/" failed: No such file or directory (2)
xs error: some files/attrs were not transferred (see previous errors) (code 23)

Exit 23 means the run finished but some entries failed, and the error summary lists the first ten. Files that succeeded are in place; nothing is rolled back. Fix the cause and run the same command again, since unchanged files are skipped.

Exit 25: the deletion limit ​

Stop when a mirror would delete too much
sh
xs -a --delete --max-delete=1 src/ dst/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 25
STDERR
xs: Deletions stopped due to --max-delete limit (1)
xs: error summary: 1 error (showing first 1)
  deletion limit (code 25): 1 error
    Deletions stopped due to --max-delete limit (1)
xs error: the --max-delete limit stopped deletions (code 25)

--max-delete stopped deletions after the limit; the transfer itself completed. Check with -n first (see preview a mirror), then raise the limit if the deletions are expected.

Exit 1: a malformed value ​

A malformed value
sh
xs --no-fallback -a --bwlimit=fast src/ dst/; echo "exit status: $?"
ACTUAL OUTPUT
exit status: 1
STDERR
xs: --bwlimit requires a nonnegative rate: fast
xs error: syntax or usage error (code 1)

PROGRESS AND OUTPUT ​

  • No progress bar in a script. Progress is on by default only when stderr is a terminal. Use --progress, --info=progress2 or --progress=json to get it on a pipe. If a bar appears where it shouldn’t, check XSYNC_OPTS, XSYNC_PROGRESS and the config file (precedence).
  • A push bar that stops below 100%. On a push, the bar follows what the receiver reports as written, so it waits for the last writes. waiting for receiver means exactly that. Older helpers cannot report writes, so the bar stays at zero until they finish.
  • File lines appear all at once. When stdout is a pipe or file, file lines are sorted and printed at the end, so the output is stable. On a terminal they appear as files finish.
  • -z on a local copy is accepted and does nothing: there is no connection to compress.

SURPRISES ON MACOS ​

  • Extra metadata on copies. On one APFS volume, -a clones files. Clones carry extended attributes, ACLs and access and creation times even without -X, -A, -U or -N, and they share storage with the source until either is modified. Use --no-clone to copy bytes instead.
  • -E means something else in Apple’s rsync. Apple’s system rsync uses -E for extended attributes. xs uses -E for executability, as modern rsync does, and -X for attributes. Write --executability when a command may fall back.
  • Cloud files. Files that exist only in iCloud (dataless files) are read normally, which can make the file provider download them.

Every example on this page is real output, captured from the current binary on Linux. Remote examples ran through an ssh stand-in on one machine. See exit status for every code.
